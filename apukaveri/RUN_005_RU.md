# Apukaveri · тестовая версия RUN-005
## Войти и попробовать
Требуется Node.js 24.22 или новее. В каталоге apukaveri выполните `node server/local.mjs`. Зависимости npm для запуска не нужны. Откройте http://127.0.0.1:8787/sandbox.html. Главная по адресу / сохраняет раннюю витрину; серверные анкеты, заказы и редактируемый каталог доступны через ссылку «Серверный стенд».

1. Зарегистрируйте demo-1@example.invalid с вымышленным паролем от 12 символов. Скопируйте код из строки TEST MAIL в терминале, подтвердите адрес и войдите. Восстановление пароля работает через тот же тестовый канал.
2. Во втором профиле браузера зарегистрируйте demo-2@example.invalid. Выберите город и категорию, включите приём и сохраните анкету. Дни недели, несколько интервалов и исключения задаются в раскрывающемся календаре. Чтобы заменить интервалы, сначала очистите день. Без исключения используется недельный график. Тестовое фото сохраняется как закрытая миниатюра 48×48 без EXIF.
3. Первый участник выбирает город, категорию, дату, начало и конец в Europe/Helsinki. При повторении осеннего часа доступен выбор позднего вхождения. Найдите помощника, добавьте в избранные, забронируйте его или отправьте общий запрос. Приоритет избранных длится пять минут. Второй участник может открыть предложение и принять его. Заказы обновляются при действиях, вручную или раз в 30 секунд на открытой вкладке. API поддерживает интервалы до 24 часов, форма задаёт начало и конец внутри одной даты.
4. Для владельца используйте файловую SQLite. До запуска задайте APUKAVERI_DB абсолютным путём к отдельному тестовому файлу вне репозитория. Без переменной данные хранятся в памяти процесса. После подтверждения первого адреса выполните `node server/grant-owner.mjs /путь/к/стенду.sqlite demo-1@example.invalid`. Откройте http://127.0.0.1:8787/admin в браузере владельца. Публичная навигация не содержит ссылку на панель.
5. В /admin можно поменять ставку и названия категории, проверить фильтры, посмотреть счета и журнал и выгрузить реестр CSV. Реальные платежи отключены. Модели split/cash включаются только для тестовых расчётов. Комиссия берётся с труда и сохраняется в заказе. В адресной заявке приоритет у ставки исполнителя, затем категории и платформы. В общей заявке ставка фиксируется до выбора исполнителя. Обе стороны отдельно подтверждают работу и наличный расчёт. При расхождении фиксируется спор. Для сценария с наличными и счётом после обоих подтверждений создаётся тестовый счёт комиссии. История сохраняет отдельные начисления, поступления комиссии, возвраты и выплаты. Ручная отметка владельца не является банковской сверкой. Для тестов разрешено подтверждать будущую синтетическую услугу.
6. Фильтры панели применяются к заказам и проводкам по времени начала заказа. Границы дат фильтра — UTC. Зарегистрированные, доступные, активные за сутки и последние 100 событий показываются по всей базе. Открытие предложения фиксируется отдельным действием. Число предложений не является статистикой доставленных push.

## Проверки и отдельный Worker
- `node --test tests/*.mjs`. Chromium: Python Playwright и `python tests/browser.py`. CHROMIUM задаёт путь к браузеру. Проверки используют временные базы и синтетические данные.
- Wrangler 4: `wrangler d1 migrations apply apukaveri-local-test --local -c wrangler.local.jsonc`, затем `wrangler dev --local -c wrangler.local.jsonc`. Все пять миграций проверены в локальной D1. Проверены каталог, регистрация, подтверждение, сессия и создание заявки с комиссией в workerd. Конфигурация содержит локальный UUID. Worker обслуживает API; для полного UI используется Node-стенд.
- Для демонстрации панели без установки Node можно собрать самодостаточный HTML: `node preview/build.mjs /путь/sql.js/dist/sql-asm.js /путь/esbuild /путь/Apukaveri-Owner-Demo.html`. Проверено с sql.js 1.13.0. Автономная копия использует те же Worker и SQL-миграции, одну вымышленную операцию 40 € и демонстрационную сессию владельца. После перезагрузки примеры сбрасываются. Этот вход не включён ни в сервер, ни в маршруты приложения.
- Для облачного preview потребуются отдельные разрешённые D1 и Worker, раздача статических файлов, закрытая тестовая почта, ограничение аудитории и проверка маршрута /admin. Не переносить консольный тестовый канал в публичный сервис.

## Дальнейшая разработка
Требования зафиксированы в ROADMAP_RU.md и ADMIN_FINANCE_SPEC_RU.md. Ближайшие задачи — MFA, полноценный жизненный цикл профиля и его удаления, проверка документов и допусков, расширение статистики предложений и срока отклика, уведомления с согласиями, тихие часы и резервная доставка. В финансах — согласованные изменения суммы, частичные отмены, пакетные счета/PDF и напоминания, сверка PSP, подписи и идемпотентность webhook. В админке — визуальный редактор, города, блокировки, жалобы, резервное копирование и восстановление. Категории сейчас читаются из БД и редактируются владельцем, создание подкатегорий остаётся в плане. Требуется общая проверка GDPR, DAC7, НДС, страхования, статуса труда, регулируемых услуг и пригодности выбранного PSP для конкретной бизнес-модели.
